## What this runbook protects

1. **CAC defines the population** — every row of a connected attachment is admitted; no row is created that is not in an attachment
2. **Transcription is not corrected** — cells are copied in their source positions and characters; anything noticed is recorded as an observation code
3. **Append-only** — rows are never deleted or rewritten; corrections are appended with a date
4. **Canonical and derived files change together** — `data/registry.json` is updated through the scripts, the CSVs are generated by `scripts/build_registry.py`, and both go into the same commit
5. **Every commit is signed; no private key enters the repository**

## Cadence

**Check the hub page (`https://www.cac.gov.cn/2024-04/02/c_1713729983803145.htm`) about once a month.** There is no strict deadline.

- CAC publishes the previous two months' attachment every two months (in 2026: 13 May, 10 July, 14 September). A monthly check picks up each attachment within about a month
- Connect any new attachment and release a new version. Several pending attachments may be connected together
- A delay does not affect correctness: attachments are delta lists, and joining them in order later still yields the full population

## 1. Connecting a new attachment

1. **Confirm the notice and attachment.** On the hub page, note the new attachment's number and label. Open that period's notice page and note its date, title and the counts in the body (new filings, new registrations, cumulative filings, cumulative registrations, as-of date). Download the PDF and save it **outside** the repository. Press figures are not used
2. **Write the `sources` entry by hand** in `data/registry.json` (attachment, `status: "not_connected"`, hub URL and label, retrieval date, `notice`). **Never edit rows by hand**
3. **Transcribe and connect:**
   ```powershell
   python scripts/extract_attachment.py --attachment 14 --pdf ..\cac-attachments\14_2026-10.pdf --out data/staging/attachment_14.json
   python scripts/register_attachment.py data/staging/attachment_14.json
   python scripts/build_registry.py
   ```
   **`extract_attachment.py` stops on a table title or header it has not seen**, meaning CAC has added a new kind of table. Following the principle in `DATA_SPEC_en.md` Section 2 (one serial-number series is one table), add a definition to `DATA_SPEC`, to `tables` in `registry.json` and to `TITLES`/`HEADER_MAP` in `extract_attachment.py`, record it with a date, then connect.
   If the counts differ from the notice, do not add or drop rows. Record the difference as `COUNT_MISMATCH_WITH_NOTICE` in the attachment's `observations`, then re-run
4. **Check the new rows by eye** against the PDF: the first and last three rows, every row with an observation code, and rows on either side of a page break
5. **Update the body and README.** Bump `version` and `snapshot_date`, add a line to the README history, and add dated notes wherever the body cites counts or distributions, leaving the original text in place. Update `llms.txt`
6. **Commit, sign and push:**
   ```powershell
   git add data/registry.json data/filings.csv data/filings_on_device.csv data/filings_anthropomorphic.csv data/registrations.csv data/filing_changes.csv data/sources.csv README.md README_en.md llms.txt docs/jp/the-china-ai-registry_JP.md docs/en/the-china-ai-registry_EN.md
   git commit -S -m "Connect attachment 14 (2026-10): filings N–M, registrations N–M"
   git push
   git verify-commit HEAD
   ```
   Do not use `git add -A`. Add a signed tag (`git tag -s v1.4 -m "v1.4"`) and create a GitHub Release

## 2. Notices without serial numbers

Record them in `separate_notices` (date, URL, title, `not_in_registry`, reason). Create no rows. When the next attachment is connected, check whether those services appear with serial numbers and append the result with a date.

## 3. Notice counts confirmed later

When a notice listed in `pending_checks` is confirmed, write it into `sources[].notice` and run `build_registry.py`. If it disagrees with the attachment, append `COUNT_MISMATCH_WITH_NOTICE`. Rows are not changed. Commit subject: `Record notice for attachment N`.

## 4. When an error is found

Row values are never rewritten.

- **(a) The error is in CAC's PDF itself** — do nothing to the data; the value as printed is correct. If no observation code caught it, mention it where the body refers to it
- **(b) Transcription error (the registry differs from the PDF)** — append a `corrections` entry to the row with date, field, `as_printed` and reason. If the cause is in `extract_attachment.py`, fix the tool, re-transcribe every connected attachment, and add `corrections` to every row whose value differs. Commit subject: `Correct F0123: <description>`
- **(c) CAC replaced a PDF (hash changed)** — do not rewrite existing rows. Append `SOURCE_FILE_CHANGED` with the new hash and retrieval date to the attachment's `observations`, re-transcribe, and record differences in the affected rows' `corrections`

## 5. Failures

Apply Section 5 and Appendices A–C of the runbook of `the-ai-forecast-registry` (wrong commit message, signing failure, leaked private key, rejected push). Two failures specific to this registry:

- **Rows in `registry.json` were edited by hand** — restore with `git checkout -- data/registry.json` and redo through Section 1 or 4
- **CSVs were edited without running the build script** — run `python scripts/build_registry.py` and commit the generated CSVs
